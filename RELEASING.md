# Releasing Black Sparrow

One tag push releases every channel with the same version:

| Channel        | Produced by                                 | Name                                                |
| :------------- | :------------------------------------------ | :-------------------------------------------------- |
| GitHub Release | `release.yml` (cargo-dist)                  | `blacksparrow-<target>.tar.xz` / `.zip` + `.sha256` |
| Installers     | `release.yml` (cargo-dist)                  | `blacksparrow-installer.sh`, `.ps1`, `.msi`         |
| PyPI           | `publish-pypi.yml`, called by `release.yml` | `blacksparrow`                                      |
| npm            | `publish-npm.yml`, called by `release.yml`  | `blacksparrow` + 7 platform packages (see below)    |

The npm platform packages are `blacksparrow-linux-x64-gnu`, `blacksparrow-linux-arm64-gnu`, `blacksparrow-linux-x64-musl`, `blacksparrow-linux-arm64-musl`, `blacksparrow-darwin-x64`, `blacksparrow-darwin-arm64` and `blacksparrow-win32-x64`. When this file was written, none of these names was taken on npm or PyPI.

`release.yml` is generated by cargo-dist from `dist-workspace.toml`; regenerate it with `dist generate` (cargo-dist 0.32.0, pinned there) and never edit it by hand. A tag with a pre-release suffix such as `v0.2.0-rc.1` builds the GitHub release but publishes nothing to PyPI or npm.

## One-time setup

Do this once, before the first tag.

### 1. GitHub

1. Repository **Settings > Environments**: create two environments named `pypi` and `npm`. Optionally add yourself as a required reviewer so each publish waits for an approval click.
2. Repository **Settings > Actions > General**: workflows may use the default read permissions; the workflows request what they need (`id-token: write` for publishing, `attestations: write` for build attestations). The repository is public, so build attestations and npm provenance work.
3. Merge this branch to `main` so the tag points at a commit that has these workflows and `schema/extract.schema.json`.

### 2. PyPI (trusted publishing, no token)

The project `blacksparrow` does not exist yet, so register a **pending publisher** at <https://pypi.org/manage/account/publishing/> (GitHub tab):

- PyPI project name: `blacksparrow`
- Owner: `Shantodotdev`, repository: `blacksparrow`
- Workflow name: `publish-pypi.yml`
- Environment name: `pypi`

PyPI currently matches the workflow file that runs the upload, which here is the reusable `publish-pypi.yml`, not the calling `release.yml` (pypi/warehouse#11096; a change to match the calling workflow is open as pypi/warehouse#20083). If the publish step fails with `invalid-publisher`, add a second publisher for the same project with workflow name `release.yml` (a project may have several), and re-run the failed job. If neither works, add a PyPI API token scoped to the project as the repository secret `PYPI_API_TOKEN`; the workflow uses it when it is set.

### 3. npm (first release needs a token, later ones do not)

npm trusted publishing can only be attached to a package that already exists, so the first release needs a token:

1. On npmjs.com create a **granular access token** with read and write access to packages (all packages, since the names do not exist yet), allowed to bypass 2FA, with a short expiry. Add it as the repository secret `NPM_TOKEN`.
2. Push the tag (below). The first release publishes all 8 packages with `--provenance`.
3. For each of the 8 packages, open **Settings > Trusted Publisher > GitHub Actions** on npmjs.com and enter: owner `Shantodotdev`, repository `blacksparrow`, workflow filename `release.yml` (the calling workflow: npm checks that one, not `publish-npm.yml`), environment `npm`, and allow `npm publish`.
4. Delete the `NPM_TOKEN` secret and revoke the token. From the next release the workflow publishes through OIDC with no secret. Optionally set each package to "Require two-factor authentication and disallow tokens".

If you would rather not use a token at all, publish a placeholder `0.0.0` of each of the 8 names by hand first, then do step 3 before the first tag.

## Releasing

1. Set the version in `Cargo.toml` and `src-tauri/Cargo.toml` (the Python package reads it from `Cargo.toml`). In `sdks/js/package.json`, set `version` and the 7 `optionalDependencies` to the same number (the staging script also rewrites them at publish time). Update `DEFAULT_TAG` in `install.sh`, and add the version to `CHANGELOG.md`.
2. Check locally:

   ```bash
   cargo fmt --check && cargo clippy --workspace --all-targets -- -D warnings
   cargo test
   cargo run --quiet -- schema extract | diff - schema/extract.schema.json
   dist plan
   ```

3. Tag and push. The tag must match the version exactly:

   ```bash
   git tag v0.1.0
   git push --tags
   ```

4. Watch the **Release** workflow run. Order: plan, builds for 7 targets (each attested), GitHub Release created, then `publish-pypi` and `publish-npm` in parallel, then announce. A failed publish job can be re-run on its own: PyPI uploads skip existing files and the npm job skips versions already published.
5. Check the result: the release page has 7 archives, 7 `.sha256` files and the installers; `pip install blacksparrow` and `npm install blacksparrow` give `0.1.0`; `gh attestation verify blacksparrow-x86_64-unknown-linux-gnu.tar.xz --repo Shantodotdev/blacksparrow` succeeds.

## If something goes wrong

- A bad PyPI or npm release cannot be replaced under the same version. Yank (PyPI) or deprecate (npm) it and publish the next patch version.
- `dist plan` complaining that `release.yml` is out of date means `dist-workspace.toml` changed: run `dist generate` and commit the result.
- The Tauri desktop shell (`src-tauri`) is excluded from releases (`dist = false` in its `Cargo.toml`); only the `blacksparrow` CLI is released.
