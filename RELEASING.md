# Releasing Black Sparrow

One tag push releases the GitHub channels with the same version. PyPI and npm are prepared but off.

| Channel                   | Produced by                                       | Name                                                     |
| :------------------------ | :------------------------------------------------ | :------------------------------------------------------- |
| GitHub Release            | `release.yml` (cargo-dist)                        | `blacksparrow-<target>.tar.xz` / `.zip` + `.sha256`      |
| Installers                | `release.yml` (cargo-dist)                        | `blacksparrow-installer.sh`, `.ps1`, `.msi`              |
| Python wheels (on GitHub) | `publish-pypi.yml`, called by `release.yml`       | `blacksparrow-<version>-py3-none-<platform>.whl` + sdist |
| PyPI (off)                | `publish-pypi.yml`, when `PUBLISH_PYPI` is `true` | `blacksparrow`                                           |
| npm (off)                 | `publish-npm.yml`, when `PUBLISH_NPM` is `true`   | `blacksparrow` + 7 platform packages (see below)         |

The npm platform packages are `blacksparrow-linux-x64-gnu`, `blacksparrow-linux-arm64-gnu`, `blacksparrow-linux-x64-musl`, `blacksparrow-linux-arm64-musl`, `blacksparrow-darwin-x64`, `blacksparrow-darwin-arm64` and `blacksparrow-win32-x64`. When this file was written, none of these names was taken on npm or PyPI.

`release.yml` is generated by cargo-dist from `dist-workspace.toml`; regenerate it with `dist generate` (cargo-dist 0.32.0, pinned there) and never edit it by hand. A tag with a pre-release suffix such as `v0.2.0-rc.1` builds the GitHub release with the binaries only: no wheels, PyPI or npm.

## One-time setup

The GitHub release needs no setup: the workflows request the permissions they use (`contents: write` to attach the wheels, `attestations: write` and `id-token: write` for build attestations). Merge to `main` first, so the tag points at a commit that has these workflows.

Turning on PyPI or npm later is optional and needs an account on each.

### PyPI (optional, trusted publishing, no token)

1. Create the environment `pypi` under **Settings > Environments**.
2. Register a **pending publisher** at <https://pypi.org/manage/account/publishing/> (GitHub tab): project `blacksparrow`, owner `Shantodotdev`, repository `blacksparrow`, workflow `publish-pypi.yml`, environment `pypi`. PyPI matches the reusable workflow that runs the upload, not the calling `release.yml` (pypi/warehouse#11096). If the upload fails with `invalid-publisher`, add a second publisher with workflow `release.yml`, or set a project-scoped API token as the secret `PYPI_API_TOKEN`.
3. Set the repository variable `PUBLISH_PYPI` to `true` under **Settings > Secrets and variables > Actions > Variables**.

### npm (optional; the first release needs a token)

1. Create the environment `npm`.
2. npm trusted publishing can only be attached to a package that exists, so for the first release create a **granular access token** (read and write, bypass 2FA, short expiry) and add it as the secret `NPM_TOKEN`.
3. Set the repository variable `PUBLISH_NPM` to `true`, and release.
4. On each of the 8 packages, add a trusted publisher (owner `Shantodotdev`, repository `blacksparrow`, workflow `release.yml`, environment `npm`), then delete the `NPM_TOKEN` secret and revoke the token.

## Releasing

1. Set the version in `Cargo.toml` and `src-tauri/Cargo.toml` (the Python package reads it from `Cargo.toml`). In `sdks/js/package.json`, set only `version` to the same number; leave out `optionalDependencies`, which the staging script adds at publish time (listing them breaks `npm ci`, since the lockfile does not have them). Update `DEFAULT_TAG` in `install.sh`, and add the version to `CHANGELOG.md`.
2. Check locally:

   ```bash
   cargo fmt --check && cargo clippy --workspace --all-targets -- -D warnings
   cargo test
   cargo run --quiet -- schema extract | diff - schema/extract.schema.json
   dist plan
   ```

3. Tag and push. The tag must match the version exactly:

   ```bash
   git tag v0.1.0
   git push --tags
   ```

4. Watch the **Release** workflow run. Order: plan, builds for 7 targets (each attested), GitHub Release created, then `publish-pypi` (wheels built, attested and attached to the release; PyPI only when turned on) and `publish-npm` (skipped while off), then announce. A failed job can be re-run on its own: the wheel upload replaces files already attached, PyPI uploads skip existing files and the npm job skips versions already published.
5. Check the result: the release page has 7 archives, 7 `.sha256` files, the installers, 7 wheels and the sdist; installing a wheel by its URL gives `0.1.0`; `gh attestation verify blacksparrow-x86_64-unknown-linux-gnu.tar.xz --repo Shantodotdev/blacksparrow` succeeds.

## If something goes wrong

- A bad PyPI or npm release cannot be replaced under the same version. Yank (PyPI) or deprecate (npm) it and publish the next patch version.
- `dist plan` complaining that `release.yml` is out of date means `dist-workspace.toml` changed: run `dist generate` and commit the result.
- The Tauri desktop shell (`src-tauri`) is excluded from releases (`dist = false` in its `Cargo.toml`); only the `blacksparrow` CLI is released.
